## 已证实的资源泄漏根因

NeoForge 21.1.250 的原生截图路径先创建 `NativeImage`，再触发截图事件。事件取消的早退路径没有关闭该图片。131 的受控试验中，连续取消 16 次，增加 16 个图片、58,982,400 字节，每张 1280×720×4，即 56.25 MiB；该次自然 GC 次数未变化，没有调用强制 GC。

`NativeScreenshotResources` 为一次原生截图建立线程内 lease。读回返回后记录该图片；原生异步 executor 接受任务前由调用端持有，接受后转移给任务的 finally。取消、监听器抛错、队列拒绝都在外层 finally 关闭；异步完成/异常也关闭；下载纹理或翻转失败则在返回之前关闭。结束时清除 lease 引用并恢复外层嵌套上下文。

这保留了原生截图事件、文件名和保存流程，不是改用浏览器预览轮询。修复后的同样 16 次取消，图片数量和字节增量均为 0。不要用强制 GC、关闭功能或减少已声明的操作来掩盖增长。

## 恢复操作与制作经验

先读真源旁边 `better-mc-remake/docs/local-mc-debug.md`。使用统一工具生成独立的新目录和 loopback 端口，按实际 GPU/内存余量安排客户端数；默认隐藏、不抢焦点。相机本身要求有效活动窗口，视觉/物理验收先协调唯一焦点 owner，再按工具文档使用可见模式，不能修改产品焦点校验来让隐藏测试通过。SSO 使用对应 owner 的既有流程。

编译历史 QA 使用 `build-qa.py --help` 所列显式本地输入与一个全新的小型输出目录；它不会创建 MC 副本或启动游戏。使用任意符合当前仓要求的 JDK21；旧 JDK 所在的 Documents/Codex 目录不属于不可替代输入。实际依赖版本和哈希由依赖清单识别，不能只看文件名：当前 MCEF 文件名仍为 2.1.6，但嵌入版本已是 `2.1.6-1.21.1-muxi.1`，和历史未打补丁的 JAR 不同。

131 的 OSHI/WMI 等待使用 QA-only 的 2000ms 超时，不重启 WMI/VM 服务。Windows 进度 JSON 替换可能遇到 sharing lock，读写应有界重试并保留失败结果，不能用强杀掩盖。`jcmd VM.native_memory summary` 与进程采样用于观察，不请求 GC。

所有自有 MC 只正常退出，回执同时核验正常退出请求、真实 exit code 和自有子进程。不能按 Java 映像名批量结束，也不动其他 owner 或 008 生产。旧 scheduled-task、131 Session2 和模板绝对路径只属于历史运行环境，恢复工作不要重新依赖它们。
