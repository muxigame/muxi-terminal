## Installed cross-instance shutdown risk

The actual MCEF2.1.6 jar in both labs hashes to `0c7696216fa5cfee659d687475873c847a9a17cc8ce3a56119a69c946eeb8772`. Read-only bytecode confirms `CefWindowsShutdownMixin` injects into `Minecraft.close()` at TAIL, invokes `tasklist`, then runs `taskkill /F /IM jcef_helper.exe` when any helper remains. It has no PID, parent-process, session, or gameDirectory scope. Therefore another installed-MCEF MC closing can destroy this instance's active helper processes. The two failing instances did not log their own cleanup message at the fault times, but the actual external triggerer remains unassigned; this mechanism is not proof of attribution.

The normal registered `MCEF-Shutdown` JVM hook already disposes this JVM's default CefClient and CefApp, leading to native N_Shutdown/TERMINATED without system-wide process enumeration. A separately identified dependency candidate should remove the global process-name fallback while retaining this normal path, then verify normal exit and no owned helper residue. The terminal must close only its own browsers, and must not globally shut down the shared CefApp. No dependency patch or extra pressure run was performed here. Such a modified-dependency result must carry its own SHA and cannot be reported as this original full pack passing.
